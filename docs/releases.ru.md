# Версии, выпуски и проверка

[English](releases.md) | [Русский](releases.ru.md)

`VERSION` задаёт версию пакета. Оба манифеста плагина должны совпадать с ней, а оба
корневых журнала изменений — описывать выпуск. Используем SemVer
(`major.minor.patch`) с `-preview.N` в период разработки. Новые возможности меняют
minor, совместимые исправления — patch, несовместимые изменения стабильной версии
— major. До 1.0 несовместимости описываем явно. Версия пакета и `schema_version`
частных данных различаются: обновление пакета не разрешает автоматическую миграцию.

## Что подписывается

- `SHA256SUMS` проверяет байты выпуска. Внутри каждого ZIP есть
  `FILE-MANIFEST.json` с версией и SHA-256 всех файлов плагина.
- Процесс выпуска подписывает происхождение всех прикреплённых файлов через
  GitHub Actions OIDC и Sigstore. Хранить личный ключ подписи не требуется.
- Неизменяемые выпуски GitHub защищают опубликованные файлы и теги и имеют
  отдельную подписанную аттестацию выпуска. Администратор должен заранее включить
  неизменяемость. Перед сообщением об успехе процесс проверяет неизменяемость
  опубликованного выпуска и его подпись. API настроек требует прав администратора,
  которые процессу публикации намеренно не предоставляются.
- Это **не** подпись каждого коммита, не Windows Authenticode, не нотариальное
  заверение приложения и не гарантия налоговой корректности или отсутствия
  уязвимостей. Для подписей коммитов нужен отдельно управляемый доверенный ключ
  сопровождающего. Нельзя создавать его от чужого имени или переписывать историю.

Исторические выпуски `0.3.0-preview`, `0.4.0-preview` и `0.5.0-preview` сохраняют
коммиты из [журнала изменений](../CHANGELOG.ru.md). Это снимки исходников,
публикуемые впервые сейчас, без заднего числа и новых аттестаций сборки.
Автоматические ZIP исходников GitHub не являются отдельно проверяемыми файлами
выпуска. Для проверяемой установки используйте именованные пакеты текущей версии.

## Скачать и проверить

На [странице выпусков](https://github.com/ilyafedotov-ops/german-business-skills/releases)
выберите [версию 0.11.0-preview.1](https://github.com/ilyafedotov-ops/german-business-skills/releases/tag/v0.11.0-preview.1) и найдите отметку **Immutable**. Доступность требует завершённой
публикации и проверки; отсутствующий платформенный архив ещё не готов к использованию.
Скачайте подходящий архив GUI или необязательный ZIP Codex/Claude и `SHA256SUMS`
в новую папку. Имена архивов приложения:

- `de-business-kit-0.11.0-preview.1-gui-windows-x64.zip`
- `de-business-kit-0.11.0-preview.1-gui-macos-arm64.tar.gz` (Apple Silicon)
- `de-business-kit-0.11.0-preview.1-gui-macos-x86_64.tar.gz` (Intel)

Примеры ниже проверяют необязательный ZIP Codex; подставьте точное имя скачанного
архива GUI для проверки приложения. Windows проверяет хеш без Python:

```powershell
Get-FileHash .\de-business-kit-0.11.0-preview.1-codex.zip -Algorithm SHA256
```

В macOS: `shasum -a 256 de-business-kit-0.11.0-preview.1-codex.zip`. Сравните результат
с нужной строкой `SHA256SUMS`. Хеш из того же недоверенного источника не подтверждает
автора. При наличии актуального необязательного GitHub CLI проверьте происхождение
архива (исторические проверки использовали 2.103.2; 2.80 не смог прочитать те аттестации):

```sh
gh release verify v0.11.0-preview.1 -R ilyafedotov-ops/german-business-skills
gh release verify-asset v0.11.0-preview.1 de-business-kit-0.11.0-preview.1-codex.zip -R ilyafedotov-ops/german-business-skills
gh attestation verify de-business-kit-0.11.0-preview.1-codex.zip --repo ilyafedotov-ops/german-business-skills --signer-workflow ilyafedotov-ops/german-business-skills/.github/workflows/release.yml --source-ref refs/tags/v0.11.0-preview.1 --deny-self-hosted-runners
```

Для строгой фиксации добавьте `--source-digest` с полным ожидаемым коммитом тега.
Не запускайте скачанные скрипты до проверки. Распакуйте в новую папку и следуйте
[инструкции приложения](../gui/README.ru.md) для GUI или
[инструкции установки skill](distribution.ru.md) для ZIP Codex/Claude. Сохраните предыдущий пакет и резервную
копию частного пространства. Установка Python и автоматическое обновление не нужны.

## Публикация сопровождающим

1. Обновить `VERSION`, оба манифеста, актуальные номера в документации и оба журнала
   изменений. Сохранить исторические даты проверок. Запустить
   `python3 -B tools/release.py check`, проверки пакета и обязательные тесты.
2. Сделать коммит и push проверенной ветки. При разрешённой публикации создать
   аннотированный тег `v<VERSION>` на точном чистом коммите и отправить тег.
   Если доверенный ключ уже настроен, предпочтителен `git tag -s`; иначе
   используются аннотированный тег и проверяемые аттестации выпуска GitHub.
   Аннотированный неподписанный тег нельзя называть криптографической подписью.
3. `release.yml` повторяет проверки Windows/macOS, PowerShell 5.1, браузеров и
   безопасности. Сборка без права записи выполняется дважды со сравнением байтов.
   Отдельное задание проверяет файлы, подписывает и проверяет происхождение,
   создаёт черновик со всеми файлами и публикует его. Код проекта не выполняется
   в задании с правом записи в репозиторий.
4. Проверить результат запуска и скачанные файлы через `gh release verify` и
   `gh attestation verify`. Отправленный тег или локальная сборка ещё не выпуск.
   Оставшийся после ошибки черновик надо проверить отдельно: процесс не заменяет
   существующие выпуски. Ошибка опубликованной версии требует новой версии.
5. Только после успешного шага 4 указать в корневом `.claude-plugin/marketplace.json`
   новый тег в `ref` и его коммит в `sha`, запустить
   `python3 -B -m unittest tests.test_packaging -v` и влить это изменение в ветку
   по умолчанию. До этого [маркетплейс на GitHub](distribution.ru.md#маркетплейс-на-github-для-claude)
   продолжает устанавливать предыдущий проверенный выпуск; неопубликованный код он
   не устанавливает никогда.

Локальная репетиция после создания точного тега:

```sh
python3 -B tools/release.py prepare --tag v0.11.0-preview.1 --output /absolute/new/release-assets
python3 -B tools/release.py verify --directory /absolute/new/release-assets
```

CI закрепляет коммиты Actions, по умолчанию имеет только чтение, не сохраняет
Git-учётные данные, ограничивает время и выделяет права публикации отдельно.
Dependabot предлагает обновления Actions/npm; npm audit и dependency review
останавливают проверки при серьёзных уязвимостях зависимостей. CodeQL анализирует
Python, JavaScript и Actions. Свежие SARIF-результаты блокируют выпуск при
security severity >= 7 или уровне error. Метаданные читаются из driver и extensions;
отсутствие результатов или неизвестные правила считаются ошибкой. Предупреждения
нужно проверять для точного ref PR/тега. Предупреждения меньшей серьёзности остаются для проверки. CODEOWNERS задаёт владельцев, но сам
не включает обязательное ревью веток. Проверки по расписанию и Dependabot начинают
работать с основной ветки после слияния изменений в неё.

Первоисточники проверены 26.10.2026: [аттестации GitHub](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations),
[целостность выпусков](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/verify-release-integrity)
и [безопасность Actions](https://docs.github.com/en/actions/reference/security/secure-use).

## Покрытие CI и предотвращение повторных прогонов

`Checks` всегда запускается и завершается стабильным **Checks gate**; фильтры
путей не пропускают workflow целиком. Каждый режим на Ubuntu проверяет пакеты,
метаданные выпуска, загруженный тег/коммит маркетплейса, локальные ссылки документации
и регрессии выбора проверок. Анализ безопасности и dependency review для PR
работают независимо с прежними событиями запуска и правилами.

- **Full:** изменения runtime, инструкций скиллов, тестов, инструментов, workflows,
  зависимостей, версии/сборки и неизвестных путей сохраняют проверки Python на
  Windows/macOS, браузеров, native PowerShell, сборок GUI и передачи артефактов.
  Теги и повторно используемые вызовы выпуска всегда выбирают этот режим и создают
  свежие файлы выпуска.
- **Documentation:** короткий путь разрешён только для обычных Markdown-файлов
  корня, Markdown внутри `docs/` или `packaging/` и корневого манифеста маркетплейса.
  Руководства/шаблоны переносимых скиллов по-прежнему требуют полного набора.
  Переименование проверяется как удаление и добавление; нечитаемый diff или особый
  режим файла выбирает full.
- **Reuse после слияния:** push в `main` может использовать завершённый успешный
  Checks из того же репозитория для связанного слитого PR. Последняя попытка должна
  записать номер PR, **full**-покрытие и точное полное Git-дерево в успешном шаге gate.
  Одного совпадения SHA головы PR недостаточно. Отсутствующие, устаревшие,
  неоднозначные или недоступные подтверждения возвращают full; PR из fork не переиспользуются.

Защита production-ветки требует **Checks gate** от GitHub Actions, а также прежние
проверки языков CodeQL, dependency review и итог CodeQL с привязкой к приложениям.
Строгое требование актуальности ветки и остальные меры защиты сохранены. Заменять
имена отдельных runtime-проверок следует только после успешного проверенного gate
и слияния его workflow; нужно сохранить идентичности security-проверок и копию
прежних настроек для отката. Старые PR должны обновиться из `main`, чтобы выдать
новый gate.

Итоговый gate отклоняет сбой планировщика/быстрых проверок, отсутствующие результаты
матриц и неожиданные пропуски до записи подтверждения. Reuse пропускает только
повторные runtime-матрицы; быстрые проверки и текущие сканирования безопасности
сохраняются. Развёртывание изменения только CI активирует workflows в `main`; оно
не заменяет неизменяемые файлы продукта и не меняет версию маркетплейса.
[Сводка проверок](validation.ru.md) отличает локальные регрессии от фактических
hosted-прогонов full/reuse/documentation.

Поведение GitHub проверено **27.10.2026**: [checkout merge-коммита PR](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request)
и [обязательные/пропущенные проверки](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks).

## Нативные архивы GUI версии 0.7.0-preview.1

Версия 0.7.0-preview.1 добавляет отдельные приложения Windows x64, macOS arm64 и macOS x86_64.

проверяет распакованный архив без внешнего Python в `PATH`. В каждом пакете
`GUI-MANIFEST.json` охватывает обычные файлы и ссылки нативных библиотек. Сборщик
архива отклоняет специальные файлы и сверяет фактически упакованные байты
с манифестом; только после этого создаётся внешняя контрольная сумма. ZIP skill
остаются независимыми пакетами.

Публикация ждёт всех платформенных сборок и проверок. Привилегированная задача
проверяет три скачанных нативных архива, добавляет их в `SHA256SUMS`, затем
подписывает и проверяет файлы прежним процессом выпуска. Код проекта и нативные
программы в этой задаче не выполняются. Побайтовая повторяемость нативных пакетов
не заявляется; проверка двойной сборкой относится к переносимым skill-пакетам.
Происхождение GitHub не заменяет Authenticode или нотариальное заверение Apple.

Фактические результаты и оставшиеся этапы — в [руководстве GUI](gui.ru.md)
и [журнале проверок](validation.ru.md). Подтвердите публикацию и проверку на странице
точной версии; документация исходников сама по себе их не подтверждает.

## Подпись настольного приложения: подготовленный следующий этап

**Подготовка проверена 26.10.2026; подпись не реализована и не проверена.**
Сертификат подписи относится к сопровождающему выпуска. Предпринимателю,
получающему помощь через MCP, браузер или установленные skills, не нужны
сертификат, аккаунт разработчика или настройка подписи приложения. Ниже описана
работа над необязательным настольным дистрибутивом.

Текущий [сборщик](../tools/build_gui.py) запускает закреплённый PyInstaller 6.22.3
с `--onedir`, без удостоверения подписи и `--windowed`, добавляет лицензию и readme,
затем записывает хеши файлов и ссылки библиотек в `GUI-MANIFEST.json`.
Результат — каталог `GermanBusinessKit`, а не пакет macOS `.app`.
[Упаковщик](../tools/package_gui.py) сверяет манифест, создаёт ZIP для Windows
или `.tar.gz` для macOS, проверяет фактическое содержимое архива и записывает
контрольную сумму. Поэтому подпись после возврата из `build_gui.py` сейчас изменит
уже захешированные файлы и должна остановить упаковку; подпись после упаковки
также нарушит контрольные суммы выпуска. Реализация после ревью должна разделить
сборку, подпись и фиксацию окончательного манифеста.

1. **Удостоверение и формат macOS.** Использовать разрешённое удостоверение
   Developer ID Application сопровождающего. Параметр PyInstaller
   `--codesign-identity` подписывает собранные бинарные файлы и включает hardened
   runtime; стандартная ad-hoc подпись не подтверждает это удостоверение.
   Проверить только необходимые приложению entitlements, итоговые подписи и
   защищённые метки времени. См. [подпись PyInstaller](https://pyinstaller.org/en/stable/feature-notes.html#macos-binary-code-signing)
   и [требования Apple](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).
   Выбрать настоящий `.app` в подходящем контейнере либо поддерживаемый
   установщик/образ диска для существующего каталога. Apple принимает ZIP,
   образы UDIF и подписанные плоские установочные пакеты; нельзя предполагать,
   что текущий `.tar.gz` или отдельный исполняемый файл поддерживает stapling.
   Для ZIP билет прикрепляется к поддерживаемым объектам внутри, затем архив
   создаётся заново. Это ещё не реализованное решение об упаковке, а не
   переименование архива. См. [собственный процесс Apple](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow).
2. **Удостоверение и проверка Windows.** Выбрать разрешённое удостоверение
   сопровождающего и способ хранения ключа. Определить перечень собственных
   исполняемых файлов для подписи, отдельно проверить подписи сторонних библиотек.
   Планируемый шаг SignTool использует SHA-256 и метки времени RFC 3161
   (`/fd SHA256`, `/tr` с выбранным сервисом, `/td SHA256`); результат проверяется
   через `signtool verify /pa /all /v /tw`. Ошибки и предупреждения об отсутствии
   метки времени должны останавливать выпуск. Сертификат, поставщик и сервис
   меток времени остаются решениями сопровождающего. См. [Microsoft SignTool](https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool).
3. **Окончательные байты и защита CI.** Завершить подпись до фиксации манифеста.
   Для macOS отправить выбранный поддерживаемый пакет через `notarytool`, проверить
   принятие и журнал, прикрепить билет там, где это поддерживается, затем записать
   окончательный перечень файлов и упаковать дистрибутив. Хранить манифест вне
   защищённых подписью ресурсов `.app`, чтобы его запись не нарушила подпись.
   Адаптировать проверку архива к выбранному формату и доказать сохранность подписей
   и билетов после распаковки. Только затем считать внешние контрольные суммы и
   аттестовать итоговые файлы. Это предложенный порядок интеграции; текущие скрипты
   его не выполняют. Обычные задания сборки и тестов PR не должны получать учётные данные
   подписи. Защищённый этап подписи должен принимать проверенные артефакты точного
   ref, использовать минимальные права и не публиковать ключи, учётные данные или
   журналы с секретами. Существующее привилегированное задание публикации по-прежнему
   не должно выполнять код проекта или бинарные файлы продукта. Получение
   сертификата, изменение секретов CI, обращения к сервису подписи, загрузка для
   нотариального заверения и публикация требуют соответствующего явного разрешения;
   этот документ ничего из перечисленного не выполняет.
4. **Подтверждение готовности.** Нужны ожидаемый издатель/Team ID, проверка
   платформенной подписи, принятое нотариальное заверение и проверка билета macOS,
   неизменность манифеста после подписи и новые пробы запуска скачанных артефактов
   на Windows, Apple Silicon и Intel macOS. Включить чистый Mac и запуск без сети,
   если выбранный контейнер поддерживает stapling; сохранить фактические диалоги
   ОС и результаты, не обещая исчезновения всех предупреждений после подписи.
   Apple рекомендует проверять распространяемый пакет на другом Mac, в том числе
   доступность билета без сети: [проверка дистрибутива](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution).
   Записывать только наблюдавшиеся результаты в [журнал проверок](validation.ru.md);
   ограничения настольной приёмки в [руководстве GUI](gui.ru.md) остаются открытыми
   до успешного завершения этих проб.
