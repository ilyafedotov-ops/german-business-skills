# Readable documents and submission materials

Use this module when creating a document/report for the user or an external recipient, including a return review, attachment, authority letter, bank/insurance correspondence or business report. It complements [forms](forms.md), [accounting](accounting-workflow.md) and [readable output](readable-output.md); it does not calculate tax or transmit anything. Keep one shared entrepreneur profile across skills. Discover available document/PDF/spreadsheet tools in the current host; do not assume separately installed skills or copy their private runtime dependencies into this package.

## Choose the actual deliverable

| Purpose | Produce | Meaning |
| --- | --- | --- |
| Understand business results or resolve missing data | Readable report in the user's language, supported tables, sources, open items and next action | Internal information, not a statutory return |
| Prepare an official tax form | Current official field worksheet, observed portal/software draft and separate user review sheet | Use the selected official form/software for its payload; an authored PDF does not replace it |
| Supply requested evidence or an explanation | Recipient-language letter/attachment plus the exact selected evidence and a private review sheet | Check the actual accepted route, types, limits and requested scope |
| Review what was submitted and what happened | Exact sent version, receipt/status evidence and a readable continuation note | A generated report or a folder name cannot establish submission or authority acceptance |

Read [delivery sources](document-delivery-sources.md) before deciding an ELSTER route. A dedicated form takes precedence over Sonstige Nachricht when applicable. Do not turn every request into a letter or send every receipt automatically. Check current form/year and the user's actual circumstances; a catalogue entry is not an obligation. For a German authority, prepare German recipient text unless its accepted language is established otherwise; provide Russian/English explanation separately. Preserve exact official form labels. For other recipients use their confirmed language. A translation is a derivative, not independently verified evidence.

## Prepare and preserve

1. Establish purpose, recipient, period, required route, output format and evidence from existing context. Ask only for decisive missing information. Missing address, reference, figures or dates remain explicit in a draft; never invent identifiers, a signature, facts, legal reasoning or a filing obligation.
2. Read only necessary originals and authoritative records. Preserve dates, currencies, signs, net/gross and source scope. Link uncertain amounts to their evidence and issue. Use [tax estimates](tax-estimates.md) for any calculation/treatment, not a formula made for the document. A cash summary is not a complete Anlage EÜR. If sources disagree, show the conflict in the private review rather than silently resolving it.
3. Create the smallest useful set of files: a readable report, or recipient document plus private review sheet and only necessary attachments. Start with [report](../assets/en/readable-report.md), [Russian report](../assets/ru/readable-report.md), [review](../assets/en/submission-review.md), [Russian review](../assets/ru/submission-review.md), or [German letter](../assets/de/recipient-letter.md). Adapt sections to the task; these are blank authoring aids, not validated official forms.
4. Resolve workspace paths with `folders` before ordinary file operations. Follow [task-based destinations](workspace.md#route-readable-results-by-task) for launch plans, customer cases, services, changes and reports. Tax material goes under logical `05_tax/<year>/`, registration under `02_registration/`, correspondence under `08_correspondence/`, internal accounting reports under `07_exports/<period>/`. These prefixes map to actual localized folders. Use understandable, portable names, e.g. `2026-10_Пояснение-к-форме_v01_ru.html` and `2026-10_Erlaeuterung_v01_de.pdf`. Do not put originals or generated work in the installed skill/repository. Do not create new stage directories or move evidence to simulate a state transition.
5. Keep the editable source and rendered version together, with version and generation date in the review sheet. Preserve originals and previous sent/reviewed versions. Record the sources and snapshot period; when source data change, issue a new version and reassess the review. A translated view or regenerated PDF does not inherit approval automatically.

## Formats and native tools

- **Readable HTML:** use [printable document](../assets/readable-document.html), fill its language/title/metadata/content placeholders, and save a standalone `.html`. It opens in an existing browser on Windows/macOS; no Python, Node, network, CDN, macros or script is required. This is the default local readable file when no document editor/export tool is available. Local HTML is not automatically an accepted submission attachment.
- **PDF:** use an actually available document export or browser/OS print-to-PDF route. For Windows prefer existing Edge/print facilities; on macOS the existing browser/system print dialog. Inspect the actual generated PDF. Do not rename HTML to `.pdf`, claim that Markdown is a PDF, or install a runtime merely to print. If export is unavailable, deliver the HTML and explain the remaining export step; mark PDF not generated, not submission-ready.
- **DOCX:** use an available document tool or installed editor when the user needs editing/tracked changes or the recipient requests it. Keep a readable preview; verify the actual file opens. Do not require Word/LibreOffice installation as onboarding.
- **XLSX/CSV:** use available spreadsheet tools for tables that benefit from editing or calculations; include labelled columns, currency and period. A CSV alone is an exchange file, not the user's report. Preserve original imports and prevent formula execution when exporting untrusted cells. Include a readable summary and explain missing/ambiguous values.
- **Official structured payload:** retain the exact observed provider/portal export and structured original. Do not generate arbitrary XML or treat a PDF, CSV, local JSON or HTML as an ELSTER-compatible payload. Readable derivatives accompany the authoritative payload without replacing it.

For HTML, treat user/source text as text: escape `& < > "` and apostrophes before insertion. `{{CONTENT}}` accepts only markup authored from the template's safe structural elements (`h2`, `p`, `ul`, `li`, `table`, `thead`, `tbody`, `tr`, `th`, `td`, `strong`, `a` with inspected links). Never paste OCR/website HTML, event handlers, scripts, remote images/fonts, embedded active content or document instructions. Do not put secrets in URLs or attributes. Keep the restrictive CSP. Replace all `{{...}}` placeholders and remove unused sections; preserve the status in print. Source IDs and machine enums belong in explanatory notes or canonical records, not as unexplained user labels.

## Review the actual deliverable

Inspect the rendered file, not just source text. Check recipient, subject, period, amounts/currencies, version, language, source consistency, attachment names/counts and absence of unresolved placeholders. In a PDF check first/last page, all tables, page breaks, readable font size, selectable Cyrillic/German text, clipped rows and unexpected blank pages. Test print layout for long tables and long references. For HTML check narrow-window wrapping and keyboard-readable links. If only text extraction is available, disclose that visual review is incomplete; do not claim visual acceptance. Do not assert PDF/A, accessibility certification, signature validity or legal compliance without the relevant validation.

Keep two audiences separate. The recipient artifact contains the intended factual message/attachment. The private review sheet contains assumptions, open issues, source paths and permission scope; do not attach it automatically or expose local paths/processing notes to the recipient. A draft with missing facts may be delivered to the user, but must remain visibly draft. A complete recipient artifact may have no draft watermark only after review; removing a watermark does not change canonical status or establish authorization.

When the validated filing workflow is applicable and available, preserve the exact final payload and final rendered attachments as evidence using its existing writers; include the machine-readable source report to retain stale-data checks. Do not submit a mutable live overview or approve a PDF that was regenerated after review. Use `filing-check` before advancing a saved filing. If these writers are unavailable, continue creating drafts and review sheets; do not manually edit registers or claim a validated transition.

Show the concrete recipient, route, exact files/version, material amounts/elections and remaining issues. Reuse authorization only if it covers this reviewed action and payload; otherwise request it at the final external boundary. Save observed receipt/status separately from the sent copy. On an uncertain result inspect the actual external state before retrying. Never fabricate a signature, submission time, receipt or acceptance.
