# Self-managed document and accounting review

On Windows without Python, use [native Windows](native-windows.md) for supported setup/intake and host tools for readable preparation. Python commands below apply only when that optional runtime is available. Do not install it by default or claim native parity for unported validated operations.

Use this module for mixed document intake, review, bank-export mapping, the monthly overview and resuming work. The user manages their own accounting and tax reporting. Consultation and a records archive are optional. Do not replace the requested accounting work with an adviser referral or export.

## What exists and what remains core work

`scripts/desk.py` implements local document/review records, bank normalization and a read-only overview. It does **not** implement a complete accounting ledger, posting engine, tax-return calculation engine or ELSTER transmission. An approved proposal is not a posted entry. A matched CSV comparison is not a closed month. Preserve separate evidence for preparation, user approval, actual posting/submission and the Finanzamt's response. Explain the specific missing capability and continue supported work in the user's chosen accounting system; never fabricate execution.

For Gmail/accounting-service records or a mixed folder, start with [existing-data onboarding](existing-data.md). `desk.py scan-folder` inventories a separate source without importing or changing it. Preserve source IDs and coverage in the private source map.

## Minimum workflow

1. Reuse the private workspace, language, activities and selected month. Use `workspace.py start` only when creation/resumption is needed. Do not force setup for an explanation. Apply the privacy review before real personal data enters model context.
2. Run `desk.py receive --root <private> --source <files...> --period YYYY-MM`. Use absolute paths for sources outside the workspace; relative paths resolve inside it. Inspect each success/error. Originals remain in their existing hash-named paths; catalog views do not move them. Repeated receipt of identical bytes records another receipt event while reusing the original. Different bytes can still describe the same transaction: link possible duplicates or corrections explicitly.
3. Retrieve a document with `catalog --document-id ID`, edit its returned `record` through a temporary input inside `00_admin/inbox`, and use `catalog-save --input <relative-file> --expected-sha256 <returned-hash>`. The assistant manages JSON; show the user readable choices, evidence and the proposed change. Do not mark their review complete without their actual decision.
4. For standalone XML use `inspect-xml --document-id ID`. The bounded UBL Invoice/CII inspector produces candidate fields, source paths and unresolved issues. It does not run XSD/Schematron, extract lines or extract embedded PDF XML. Keep technical validation, arithmetic and tax review separate. Preserve PDF/attachments pending an available assessed extractor; do not assert that embedded XML is absent. See [document sources](document-sources.md).
5. Use `template --kind proposal` and `template --kind extracted-field` to prepare a draft. Save through `proposal-save --input <relative-file>`. Retrieve existing proposals with `record --collection proposals --id ID`; edit `editable` and use the returned hash. Review original wording/location, normalized values, dates, lines, rates, totals, treatment and missing facts with the user. Register current period-specific source checks before approval. Finalized proposals require a new linked correction; original evidence remains unchanged.
6. For a bank export, use `template --kind bank-mapping`, then `bank-preview --document-id ID --mapping <relative-file> --period YYYY-MM`. Use an empty string for no grouping separator, not null. Show the mapping, row count, signs, dates, currencies, sample rows and overlap notes. `bank-approve --preview <path> --expected-sha256 <hash> --reviewer <name> --evidence <private-file>` applies the reviewed preview. Record actual approval evidence, not an invented user decision. Existing native transaction IDs are account-scoped; overlapping imports are rejected. Generated row IDs need additional overlap review.
7. Reconcile the normalized bank CSV against actual supplied accounting records with `workspace.py reconcile`. See the [CSV contract](workspace.md). Do not construct a matching ledger from the bank export and present it as independent accounting evidence. Missing ledger records are a capability/input gap, not successful reconciliation. The overview recomputes report results and checks source hashes before trusting them.
8. Run `desk.py overview --root <private> --period YYYY-MM [--language en|ru]`. Open `00_admin/overview.html` or Markdown. The five views are Overview, Inbox, Needs review, This month, Accounting & tax. Save substantive tasks/questions/decisions through `workspace.py entry`; generated pages are not an editable task list. Preserve deadlines with their source and distinguish a stated response date from a verified legal deadline.
9. For filing preparation, route to [forms](forms.md) and [preparation](preparation.md). Report draft, approval, actual submission evidence and authority response separately. The desk cannot transmit to ELSTER or establish a full accounting closing. Finish with the user's next accounting/reporting action and resume from saved records later.

## Contracts and locations

`00_admin/documents.json` preserves the original index. Additive `00_admin/casework.json` schema 1 stores `documents`, `receipts`, `proposals`, `source_checks`, `observations`, `bank_imports`, `inspections`. Reading a legacy workspace derives default catalog entries without rewriting its index. Unsupported schemas require explicit conversion; no migration command is provided.

| Record | Validated contract |
| --- | --- |
| Catalog | Document ID, readable title, type, activity IDs, organizational periods, separate invoice/service/received/due/paid dates; review state and reason; existing task/question/decision/correspondence links; payment references and typed document relations |
| Extracted field | `raw`, `value`, `location`, `status`, `reviewer`, `note`; status `extracted`, `reviewed`, `unavailable` or `rejected`; normalized decimals remain strings, dates ISO, missing values null |
| Proposal schema 2 | Document/activity/period, `fields`, `lines`, `tax_breakdown`, `proposed_treatment`, `review`, `supersedes`; initial draft, then review outcome; saved original hash and arithmetic issues are derived |
| Source check | Immutable ID, HTTPS URL/title, check date, applicable year/month, assumptions, conclusion, review-after date, reviewer and preserved evidence file/hash; URL syntax is not proof of authority or legal correctness |
| Observation | Separate proposal/provider/record ID, observed state/date, reviewer and preserved evidence; records supplied evidence, does not query a provider or submit anything |
| Bank mapping | Explicit delimiter/encoding, date format, decimal/grouping separators, signed or credit/debit columns, sign convention, account ID and currency; preview and normalized CSV retain fingerprints |

A `lines` row is `{ "line_id": "line-1", "fields": { ... } }`; allowed field names are `description`, `quantity`, `unit_price`, `net`, `tax_rate`, `tax`, `gross`. A `tax_breakdown` row is `{ "tax_id": "rate-1", "fields": { ... } }` with `tax_rate`, `net`, `tax`. Every value in `fields` uses the full extracted-field contract. Header fields also allow `invoice_number`, `invoice_date`, `due_date`, `service_from`, `service_to`, `receipt_date`, `payment_date`, `supplier_reference`, `customer_reference`, `supplier_country`, `customer_country`, `currency`, `description`, `amount_due`. Decimal amounts and normalized dates remain strings. Do not attach provider payloads or unsupported keys to these records.

For proposal details use the [input template](../assets/proposal.json), [field template](../assets/extracted-field.json) and runtime help. Approval requires reviewed core invoice fields and period-applicable source checks. Optional supplied lines/rate breakdowns are checked; missing breakdowns or unsupported allowances must remain a documented substantive review issue, not a claim of full invoice validation. Dates and `amount_due` remain distinct from gross and observed payment. All reviews require actual inspection; a text reviewer name is not authenticated identity.

## Optional personal archive

Only when useful or requested, run `desk.py archive --root <private> --period YYYY-MM`, then `verify-archive --bundle <absolute-folder-or-zip>`. The archive contains selected originals, linked records/evidence, reconciliation and a manifest of inclusion/exclusion/open items. It is a generic records snapshot, not a complete backup, DATEV import or filed return. `integrity: verified` concerns bytes; `prepared_with_open_items` / `prepared_for_self_review` concern this snapshot, never accounting or filing completion. Explicitly excluded bank documents and their known derivatives are omitted. Any unexpected evidence dependency requires review. Sending an archive is a separate authorized action.

## Recovery and limits

Writers use the shared lock and atomic individual JSON replacement with history. Original copying, receipt events, normalized files and audit writes are separate operations, not a multi-file transaction. After interruption inspect outputs, hashes, original verification and history before retrying; preserve orphaned/unknown files. Do not delete or overwrite them to bypass a collision. Generated views may be stale; regenerate after record changes. The static dashboard has no server, external assets, model API or write actions. Offline utilities do not imply local AI inference. Tested utilities are separate from native Windows/macOS desktop acceptance.
