# ELSTER transmission: verified route and implementation limits

Checked **2026-10-25**. Applies to integration planning on that date; supported forms, tax periods, SDK releases and authentication options must be checked again for an actual filing. This note establishes neither a filing obligation nor the correctness of a particular return.

## Supported route

- [ELSTER developer guidance](https://www.elster.de/elsterweb/infoseite/entwickler) identifies **ERiC**, a C library supplied free for integration into tax/accounting software. It validates data and transmits it through an encrypted connection to the tax administration's receiving servers; after successful server feedback it can create a PDF. The application supplies its own interface. The documented onboarding requires manufacturer/developer registration, review by the Bayerisches Landesamt für Steuern, developer-area access, SDK download and a manufacturer-ID application. **Consequence:** a generic HTTP client or locally generated XML is not an implemented transmission route.
- [ELSTER legal guidance](https://www.elster.de/elsterweb/infoseite/rechtliches) identifies ERiC as required for transmission of officially prescribed datasets and requires the officially designated interface for the relevant tax period/time. **Example:** structurally valid JSON or a reviewed worksheet for 2026 does not establish an accepted 2025 UStVA dataset. Do not invent endpoints, XML schemas or Kennziffer mappings.
- [ELSTER entrepreneur guidance](https://www.elster.de/elsterweb/infoseite/unternehmer) supports the separate existing route of preparing a return in **Mein ELSTER** or using ELSTER-compatible software. Authenticated transmission requires registration; the UStVA transmission protocol is evidence of electronic filing for the user's records. **Consequence:** supported user-assisted portal filing can coexist with local preparation, but the local tool must not claim it transmitted anything merely because a draft was exported.

## Access, distribution and test prerequisites

[Developer registration](https://www.elster.de/elsterweb/registrierung-entwickler/form) says the development toolkit is free after registration, with no entitlement to an account and possible withdrawal of access. Registration was inspected, not submitted.

The official [ERiC page](https://www.elster.de/elsterweb/entwickler/infoseite/eric), [interface descriptions](https://www.elster.de/elsterweb/entwickler/infoseite/schnittstellenbeschreibungen) and [applications/resources](https://www.elster.de/elsterweb/entwickler/infoseite/ressourcen) all redirected to developer login during this check. No authenticated documentation or SDK was accessed. Therefore the following remain **unverified prerequisites**, not invented guarantees:

- Current SDK version, supported host/CPU combinations, ABI, exact operations, supported datasets and tax years, release/update policy and error/receipt semantics.
- SDK licence and redistribution conditions, including whether binaries may ship in this MIT-licensed package. Free availability for integration does not establish unrestricted redistribution or relicensing. Keep restricted assets out of the repository until the actual terms have been reviewed.
- Official test-mode configuration, permitted synthetic identifiers, test credentials/certificates, target selection, any test/approval obligations and separation from production. Obtain the current developer documentation before implementing a test transmission. No test marker, sandbox URL or certificate format is inferred from forum posts or old examples.

[ELSTER app guidance](https://www.elster.de/elsterweb/infoseite/apps) states that ElsterSecure currently authenticates login to Mein ELSTER and does not yet support transmission from other vendors' tax software. **Example:** a successful phone login does not establish authentication for an ERiC integration. Keep secrets/certificates out of profiles, source, chat and logs; use a separately reviewed host mechanism if a future adapter needs them.

Context7 was checked for `ELSTER ERiC`; it returned unrelated libraries, so no official SDK documentation was available there. Public first-party ELSTER pages above are the evidence used here. This is not proof that no other supported product or private documentation exists.

## Repository evidence and truthful local scope

At inspection, [workflows.py](../scripts/workflows.py) implements offline field preparation with `draft_only` routing; [preparation.md](preparation.md) explicitly keeps `filing_status` at `not_submitted`. The tracked-file/import inspection found no ERiC binary, header, binding, dependency manifest or live ELSTER transport. [forms.md](forms.md) contains user-assisted portal instructions, not a connector. These are local source observations, not live integration tests.

Implementable without credentials or external writes: durable filing cases linked to a frozen preparation/payload digest; explicit review/authorization records; append-only transmission-attempt evidence; manual import and verification of retained receipt files; separate authority-response records; readiness checks that report unavailable transport. Label mock transport results as synthetic and keep them outside real filing state. This does **not** complete ERiC transmission, official schema validation, receipt authenticity validation or live status lookup.

## Proposed lifecycle invariants

These are engineering requirements inferred from the evidence and the existing [forms workflow](forms.md), not a verified ERiC wire protocol:

1. Bind review and explicit authorization to the exact taxpayer/workspace, form, period, destination, payload digest and revision. A material payload change requires a new review/authorization record. Local approval is not a transmission receipt.
2. Record an attempt before calling a future transport, with one active attempt per filing revision. Serialize changes; retain attempt identifiers and any returned server identifiers. Distinguish local duplicate prevention from server-side idempotency, which has not been established.
3. After a timeout, crash or ambiguous reply, retain `submission_unconfirmed`. Block blind retry until supported official status evidence or a documented reconciliation procedure resolves the attempt. A changed local filename/digest must not bypass an unresolved attempt for the same filing.
4. Only retained, linked transport/portal evidence can support a confirmed transmission result. Store receipt bytes/digest, origin, timestamp, identifiers and whether confirmation was imported manually or obtained by a verified adapter. User-entered text or a synthetic receipt alone cannot prove official acceptance.
5. Keep receipt, authority response, payment and subsequent correction separate. A receipt shows transmission evidence; do not derive substantive tax approval or finality from it. Preserve the earlier attempt when creating a correction/superseding revision.

No registrations, filings, test transmissions, restricted downloads or account actions were performed. Live transport readiness remains blocked on authorised developer access, current documentation/licence review, a separately reviewed adapter and synthetic end-to-end verification before any explicitly authorised real filing.

## Limited local EÜR-oriented records and report preparation

The authoritative accounting route is a welcome/onboarding choice: local records or an existing third-party system, with no preselected route. This product decision does not establish eligibility for EÜR or change a tax regime. Record the chosen system and scope; do not silently create two authoritative sets of postings.

- [EStG § 4(3), consolidated EStG](https://www.gesetze-im-internet.de/estg/BJNR010050934.html) permits eligible taxpayers who are neither obliged to keep books/regular accounts nor actually do so to determine profit as business receipts less business expenses. It excludes qualifying third-party pass-through items and still requires asset/depreciation rules and asset records. **Consequence:** calling an incoming bank item income, or expensing every paid asset immediately, cannot implement complete EÜR. Eligibility must be established separately. The whole-statute page supplied the text; direct § 4 fetches timed out.
- [EStG § 11](https://www.gesetze-im-internet.de/estg/__11.html) generally assigns receipts to the calendar year received and expenses to the year paid, with exceptions including recurring items near year-end and certain advance payments. **Example:** preserve invoice, service and payment dates separately; do not allocate solely from invoice date or mechanically treat every January payment as belonging to January. This check used the official indexed statute text because the direct page extract omitted the body.
- [Official ELSTER EÜR instructions for 2025](https://www.elster.de/eportal/helpGlobal?themaGlobal=help_euer_ufa_77_2025) distinguish receipts/expenses, profit corrections, asset schedules, and drawings/contributions. They separately address collected/refunded VAT, deductible input VAT and VAT paid to the tax office; expense presentation differs for Kleinunternehmer. They also address noncash private use. **Consequence:** keep VAT categories and owner cash movements distinct; a bank transfer is not sufficient classification evidence. These are **2025** instructions, not verified 2026 field mappings.

Recommended implementation boundary (engineering inference): preserve evidence-linked cash records with payment date, amount/currency, business/activity scope, source transaction/document, category, reviewer and revision history. Report only **recorded and reviewed cash receipts, cash expenses and their arithmetic difference**, with excluded/unclassified counts and outstanding tax reviews visible. An internal transfer between the same owner's accounts must not be counted twice as income/expense; retain both legs for reconciliation. Distinguish such transfers from private drawings/contributions, loans, refunds and asset-related cash movements rather than treating them as one generic exclusion. Classification approval is not evidence that all transactions were imported or that their tax treatment was correct.

Until separately implemented and validated, flag assets/AfA/GWG, private-use or mixed-use adjustments, restricted/non-deductible costs, loans/principal, VAT regimes and tax-office payments, foreign-currency conversion, year-end timing exceptions, prior-year corrections and changes of accounting method as unresolved specialist calculations. Do not silently include them in a figure labelled statutory taxable profit. A cash report can preserve these records and supplied classifications while refusing to certify a complete Anlage EÜR or a VAT return. EÜR payment timing also does not establish VAT Soll-/Istversteuerung; [official registration help](https://www.elster.de/eportal/helpGlobal?themaGlobal=help_fseeun_202501) treats VAT timing and permission for cash-based VAT separately.

**2026 mapping access limit:** the [BMF first-party publication listing](https://www.bundesfinanzministerium.de/Web/DE/Service/Publikationen/BMF_Schreiben/bmf_schreiben.html?gtp=bbp) indexed an **Anlage EÜR 2026 publication dated 2026-09-01**. Direct BMF page fetches returned HTTP 503 during this check, so the 2026 publication body/form attachments were not inspected. This is not a claim that the 2026 form is unpublished. No 2026 line/Kennziffer mapping, calculation coverage or ERiC schema was verified. Keep reports independent of guessed field numbers; inspect the actual period-specific official instructions and licensed developer interface before adding a mapped form export. Local arithmetic tests cannot resolve that access gap.
