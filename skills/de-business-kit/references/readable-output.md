# Human-readable results across the project

Apply to every module, regardless of engine or connector. Canonical JSON, hashes and logs remain machine/evidence records. The assistant explains them and provides readable results; users should not need to edit JSON, remember prompts or decode CLI enums to continue.

For a simple question give a direct answer without requiring a workspace or file. For durable work create/update a user-language Markdown or standalone HTML summary, or use the existing generated report. Use [document authoring](document-authoring.md) when printing, editing or sending a document. This is a skill-level output contract: several CLI commands still return JSON only; they do not automatically create every format.

Every substantial result answers: what was done; which period and sources it covers; what is verified versus unresolved; what the user needs to decide/do next; and where the readable file/original is. Link the actual resolved paths. Use meaningful names and explicit version/date. If a write fails, preserve the user's entered material and explain what was not saved; do not claim success or a reminder without observed evidence.

| Workflow | User-facing result |
| --- | --- |
| Onboarding / source connections / folder scan | What was found, selected/excluded, not accessible, whether anything was imported, and the next action; existing source map where suitable |
| Invoice extraction / proposal review | Original alongside readable fields, amounts, evidence locations, corrections and unresolved treatment; no unexplained JSON |
| Banking / payment matching | Currency-separated totals, matches, unmatched movements, fees/refunds and coverage limits; no unsupported tax conclusion |
| Local or external accounting | Readable period report and authoritative system; recorded cash movement remains distinct from taxable profit or statutory EÜR |
| Tax forms / authority letters | User-language explanation, recipient-language draft where needed, actual official route, issues, exact files and observed submission state |
| Banking / insurance / provider research | Needs, current-source comparison, material costs/exclusions and next decision; no unobserved connection or purchase |
| Status / resume / diagnostics / archive | Current evidence-backed state and next useful step; an archive is optional and not a backup, filed return or mandatory accountant handoff |

Use short paragraphs, labelled tables and explanations next to difficult fields. Retain exact German form labels with a local-language explanation. Unknown is not zero; absent receipts are not matching transactions. Never translate `draft`, `reviewed`, `posted`, `submitted` or a receipt into legal correctness or authority acceptance. Do not add signatures, seals, official branding or visual status cues suggesting approval that did not happen.

Generated views are snapshots of canonical records, not a second task register. Save decisions through the existing validated writers when available; a manually edited report cannot mutate them. Keep source fingerprints in canonical evidence and identify the reviewed version. Revisions preserve earlier reports and sent documents. For sensitive recipient material, keep the private explanation and machine records separate from the intended attachments.

For screenshots and visual evidence, apply the [privacy check before sharing](privacy.md#check-screenshots-before-sharing).
Prefer minimized text; inspect the exact redacted derivative and its filename,
caption and link target before including it in chat or a readable report. Never
embed a raw private screenshot merely because its local path is available.
